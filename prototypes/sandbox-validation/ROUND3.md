# #8 补充验证：回收、迟到发布、清理故障与容器外期限

2026-11-12，按用户审阅后的要求补齐三组缺口，并验证“管理服务失效后仍有停止上限”的最小方案。此轮结果取代第二阶段报告中对恢复和迟到发布过宽的表述；第一、二阶段记录保留为历史证据。

## 选定方案

新增一个独立 Compose `watchdog` 服务，复用现有 Java/JRE 镜像和 Docker CLI，没有新依赖、数据库、队列或对外接口。业务主应用、沙箱管理服务与看门狗是不同容器；看门狗无网络，仅持有 Docker socket 和自身健康记录目录，不持有模型、数据库或管理 API 凭据。

- 管理服务继续使用 AgentScope Java 2.0.4 创建/执行受限任务；处理容器不获得 Docker socket 或看门狗目录。
- 看门狗按实例标签选取本实例任务，使用 **Docker 引擎记录的容器创建时间** 加固定 15 秒作为探针期限。处理程序不能通过更改工作区文件延长期限。
- 每 250 ms 开始下一轮扫描（加上本轮 Docker 操作耗时）；单个看门狗 CLI 调用最多等待 2 秒。到期强制删除后，再查询确认容器实际消失。
- 管理服务只读看门狗健康记录，记录超过 2 秒或不可读时拒绝新建任务。健康记录只在成功扫描后刷新；看门狗由 Compose 配置自动重启。存活任务在看门狗恢复后重新按原始创建时间核对。
- 删除处理镜像内的 `task-init.sh`，第二阶段的进程内计时器不再参与任何期限保证。

15 秒是故障注入探针参数，不是生产文件处理 SLA。测试将“从 Docker 创建到确认删除不超过 25 秒”设为本机样本的断言；不能从单次通过推导所有负载下的最坏延迟。生产期限和扫描/并发预算需要在目标机器上验收。保证管理服务失效时可独立回收的前提是看门狗、Docker 引擎、宿主调度与时钟仍可用；没有宣称 Docker/宿主也失效时仍能保证墙钟停止上限。

## 复跑

```sh
cd prototypes/sandbox-validation
python3 verify_managed.py
```

脚本执行原管理接口/处理测试，再执行本轮所有新增场景。首次构建需要公开 Maven 依赖和已固定摘要的基础镜像。本轮只处理合成资料；所有容器、网络均按唯一运行标签创建和定向清理。控制服务无宿主端口。

`fault-docker.sh` 和只读 `/faults` 挂载仅是测试夹具：由宿主验证脚本控制，在管理服务的真实 Docker CLI 路径注入删除拒绝或通信失败。它不是模型工具、HTTP 接口或生产能力；看门狗不使用该夹具。没有停止共享 Docker daemon，也没有影响其他项目。

## 三组补证

| 场景 | 真实路径与判定 |
| --- | --- |
| **仍存活的遗留容器回收** | 创建两个长时间处理任务，强杀主应用和管理服务；确认两个子进程的心跳继续增长，容器仍存在。立即重启管理服务，由其启动回收逐一删除两个容器，日志必须各有 `RECOVER_REMOVED`，任务查询为 `INTERRUPTED / CONFIRMED / STOPPED`。同时创建不同实例标签的对照容器，确认未被删除。未先等待自动过期。 |
| **迟到成功结果进入真实提交入口** | 正常远端转换先经现有 `SandboxProbe.Task.publish()` 发布旧版；另一任务在管理服务完成后，主应用先取消其业务任务，再发起新的 HTTP 查询接收远端 `SUCCEEDED` 结果，将结果传给同一实际提交方法。断言返回拒绝，旧文件字节不变，没有 `version.next`，重复送达也拒绝；正常提交对照成功。 |
| **清理失败、持久记录和重试** | 分别注入 Docker 删除拒绝、管理服务到 Docker 的通信失败。实际取消接口返回 202，业务状态 `CANCELLED`；`cleaned=false / RETRY_PENDING / UNKNOWN` 写入持久记录，容器子进程仍有心跳。此时新任务返回 503。解除故障后定时重试确认实际删除，状态转为 `CONFIRMED / STOPPED`，业务仍为 `CANCELLED`。 |

成果提交仍是单 JVM 文件原型，验证的是跨服务成功响应进入实际发布条件检查的行为，不是 MySQL 事务、分布式并发或断电持久性验收。

## 独立期限与故障控制

- 移除容器内计时器后，确认处理容器没有 `/opt/task-init`、Docker socket 或看门狗目录；向工作区写入很远的伪造期限。
- 强杀主应用及管理服务，确认处理子进程仍前进，之后由仍运行的看门狗按 Docker 创建时间回收。
- 看门狗日志同时记录发现到期的容器年龄、确认删除时的年龄与绝对时间；验证脚本核对实际删除年龄在 15～25 秒内，并确认对照容器不受影响。
- 主动停用看门狗，健康记录过期后主应用的新请求被拒，管理登记目录没有新增任务；恢复看门狗后正常请求成功。

业务状态、进程状态和清理状态分开：业务取消不等于进程已停止，只有查询确认资源不存在后才报告清理完成。清理异常不会被吞成成功；重试期间拒绝新增任务，避免未清理资源持续累积。启动回收只针对本实例标签，并核实删除后再恢复服务。

## 接入与收口结论

最小方案为主应用 + 沙箱管理服务 + 独立看门狗，仍使用单机 Compose；不把完整智能体运行服务拆出主应用。相较第二阶段多一个很小的监督组件，并把高权限 Docker 信任边界扩展至该看门狗。它不接受任意调用，只扫描和终止本实例到期任务，但仍持有完整 daemon 权限，不等同于 rootless 或 Docker API 权限裁剪。

三组补证与外部期限结果支持 #8 的集成可行性结论，#6 应以此更新执行环境管理与部署责任。最终审阅和关票独立于生产上线；本轮不将生产 Linux、真实解析器、正式身份/密钥、数据库提交、备份恢复、内核逃逸或全宿主失效宣称为已通过。
