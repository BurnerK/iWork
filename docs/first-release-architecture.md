## 范围与技术栈

面向一个部署实例中的少量内部用户，完成账号与模型配置、个人会话和项目空间、直接提供资料、后台任务、文字文档成果及独立版本的闭环。沿用 [首版范围决议 #3](https://github.com/BurnerK/iWork/issues/3#issuecomment-6816313871)，不扩大到 IM、对外网关、Skill/MCP、平台知识库、市场、多智能体或其他成果类型。

主应用采用模块化单体：Java 21、Spring Boot、AgentScope Java；Web 使用 Vue 3、TypeScript，构建后随应用交付。采用 MySQL/InnoDB 与持久文件目录。依赖具体版本与组合兼容性尚未冻结。

## 模块责任与接口

| 模块 | 责任 | 向其他模块提供的主要能力 |
| --- | --- | --- |
| 身份与资源 | 登录、资源归属与访问授权 | 确认调用者、校验资源访问；管理员管理权限不自动授予私人内容读取权 |
| 会话与任务 | 消息与任务记录、幂等、同会话互斥、取消、后台生命周期 | 提交、查询、取消任务，读取任务事件与状态 |
| 智能体运行 | 应用指令与模型配置，组织 AgentScope 模型及内置工具调用 | 执行已授权任务、传递取消、报告进度与调用结果；不自行决定业务终态 |
| 成果与文件 | 原始资料、执行工作区、正式成果与版本 | 提供获准资料、准备成果内容、在任务状态允许时提交正式版本 |
| 模型与用量 | 模型配置、使用授权、额度预占与核算、逐调用记录 | 授权并登记模型调用，记录供应商回报或估算，结算并释放预占 |

这些是逻辑模块接口，不要求模块间 HTTP 调用或独立服务。领域名称沿用根目录词汇表。未来接入 IM、外部应用时，调用者、资源归属与预算归属仍须分别表达；不提前实现这些入口。SDK 状态与工作区不是业务数据的权威来源。

长期约束沿用 [领域与归属决议 #2](https://github.com/BurnerK/iWork/issues/2#issuecomment-6814042167) 和 [网关边界决议 #5](https://github.com/BurnerK/iWork/issues/5#issuecomment-6817018315)：个人使用者授权与 IM/外部应用的服务授权分开，不借用创建者私人凭据；智能体网关、运行服务、模型网关保留逻辑责任边界，不预先拆成三个服务。后续知识库保持独立权限；智能体与 Skill 的分享为独立副本，私人授权不随副本交付；会话与成果分享为固定快照或指定版本。个人长期记忆与视频创作空间保留独立生命周期，不并入项目空间。

## 持久化与主要流程

MySQL 保存身份与授权、配置、会话与任务、幂等关系、成果版本及文件索引、模型调用与额度记录。持久目录分别保存原始资料、执行工作文件和正式成果内容。项目空间引用会话与成果，不接管其生命周期；删除项目不自动删除关联内容。

1. 校验调用者及资源权限，以短事务建立任务身份、幂等记录及同会话执行约束；同会话不排队，不同会话可在部署容量内并发。
2. 任务在服务端后台执行，浏览器连接只负责提交和观察。模型调用与文件处理不持有覆盖整段执行的数据库事务。
3. 受控文件工具将获准文件交给隔离执行环境，结果先作为未发布内容准备完整。
4. 取消与正式成果提交通过相同的任务状态边界协调：提交事务校验终态并登记版本；取消已生效则拒绝迟到发布，保存失败不改变旧版本。数据库未登记的临时文件由清理流程处理。
5. 每次实际模型调用分别记录用量来源与完整性，缺失时估算内部额度，收尾释放预占，供应商实际消耗仍可待核实。
6. 主进程重启保留已保存内容，将遗留未完成任务标记中断，不自动重跑。原型中的单 JVM 文件替换不直接充当生产实现。

## 部署与文件处理隔离

单台 Linux 服务器使用 Docker Compose 部署主应用和 MySQL，资料及成果使用持久目录。首版不增加 Redis、消息队列或 Kubernetes；接受维护窗口内停机。

文件处理优先评估 AgentScope Java 官方 Docker 沙箱能力，运行平台预置解析与转换程序，仅向模型开放受控业务工具。执行环境只获得本次所需文件，不获得主数据库或模型凭据；配置资源、网络、挂载和运行权限限制。自定义 Java 工具需要显式接入沙箱，不会自动迁移进去。

在确定具体接入方式前，验证主应用运行于 Compose 时如何以受控权限管理任务容器，避免将容器管理接口暴露给模型或文件处理环境。验证文件边界、跨任务隔离、取消与超时后容器内程序的实际终止、容器及工作文件清理。若官方接入能力无法满足这些要求，返回该隔离决策讨论，不默认改成宿主直接执行。

### 架构收口待办：官方 Docker 沙箱接入验证

该验证用于回答：主应用保持模块化单体及 Compose 部署时，能否复用官方能力完成受控文件处理，而不破坏权限、取消及成果发布边界？容器管理权限或生命周期问题可能改变部署接入方式，因此按 #6 的收口要求，已创建 [沙箱接入验证任务 #8](https://github.com/BurnerK/iWork/issues/8)，作为 #6 的收口前验证，不能把该项仅作为已完成架构的普通验收。

- 固定所用 SDK 版本，验证 Compose 中主应用到沙箱的管理路径与权限，记录所需主机能力。
- 用合成资料运行一个平台预置文件处理工具，验证自定义工具确实在容器内执行，模型无法调用通用 shell。
- 验证跨用户及跨任务文件访问拒绝、数据库与模型凭据不可见、网络及资源限制生效。
- 验证取消、超时与主应用异常退出后，容器内处理进程的实际终止、清理和正式成果保护；不能仅凭宿主 `docker exec` 客户端退出判定处理已停止。
- 记录可复现证据、失败情况和接入结论；若必须调整隔离边界或部署结构，回到相应决策讨论，再判断 #6 是否可收口。

## 升级、恢复与验证

升级前备份；恢复时协调 MySQL 记录与持久文件。服务器规格、正式模型服务、备份位置与恢复目标在部署准备时落实。首版不宣称多机高可用或已通过断电恢复验证。

实现后的核心验收覆盖真实用户权限、幂等与同会话互斥、浏览器断连继续执行、取消与发布竞争、保存失败保留旧版、重启中断、逐调用估算及重复回报不重复扣减，以及数据库与文件的备份恢复。文件处理隔离另按上述验证项验收。已有原型证据支持业务语义，不替代这些生产检查。

额度估算算法、无法可靠估算的处理、差额调整，具体 API 字段、重试参数、依赖版本及运维参数留到相应实现设计；本轮仅确定架构方向和职责边界。

## #8 接入实测补充 · 2026-11-12（待审阅，不变更已确认决议）

[探针及证据](../prototypes/sandbox-validation/README.md) 已在 Compose 主应用与真实 AgentScope Java 2.0.4 DockerSandbox 上完成。受控工具、任务容器隔离及资源限制得到实测支持；官方上传的 docker cp 路径在只读 rootfs 下失败，归档传输可用。SDK stop、执行超时与 Java 调用取消均不能保证容器内程序终止，主应用强杀也留下运行中的容器。显式 shutdown、重启后定向回收和迟到发布保护已由探针验证；无独立看门狗，不能承诺主应用未恢复时自动回收。

当前可运行路径依赖主应用挂载普通 Docker socket，具有该引擎完整管理权。该权限范围尚未由用户接受。建议讨论增加受限沙箱管理服务，或明确接受主应用直连的权限；两者均需把生命周期补充机制纳入实施。此处只记录验证结论与建议，不把新部署组件写成已确认设计。#8 和 #6 保持开放；本机 OrbStack Linux 容器结果不替代 Linux 生产部署验收。

## #8 审阅后决定 · 2026-11-12

用户审阅第一阶段证据后，明确选择**增加受限的沙箱管理服务**，接受增加一个 Compose 部署组件并继续验证。此决定取代上述待选择状态：主应用不直连 Docker socket，只向管理服务提交获准资料和固定处理操作；管理服务持有容器管理权限，不接收主数据库和模型凭据，不承担完整智能体运行、业务终态或成果版本权威。

管理接口不得接受任意镜像、命令、宿主路径、挂载或 Docker API 转发；须验证服务身份和任务访问权限，固定资源与网络限制。取消/超时应销毁任务容器并确认实际删除；持久记录任务与容器关联，启动时定向回收，不自动续跑。第二阶段已使用独立 Compose 主应用/管理服务探针验证接口边界与故障处理，详见探针报告；生产凭据分发、身份鉴权、Linux 实机、数据库事务和部署恢复仍需实施验收。

管理服务本身仍持有高权限。固定镜像内部的生存期仅验证普通进程故障，不构成对恶意处理程序的强制期限；对不可信解析器需容器外执行期限并另验。#8/#6 暂不关闭，待最终验证证据审阅；不改变已确认的模型额度和其余首版范围。

## #8 补证与容器外强制期限 · 2026-11-12

用户要求补齐三组验证，并明确强制执行期限必须在处理容器外、管理服务失效后也要有停止上限。按此授权选择最小方案：增加独立 Compose 执行看门狗，复用现有运行镜像，无对外接口、业务凭据或数据库依赖。它根据 Docker 的容器创建时间和本实例标签回收逾期任务；处理容器内计时器移除。看门狗健康记录过期时管理服务拒绝新建任务。

此修订取代前文“只有管理服务挂载容器管理接口”的描述：管理服务与执行看门狗分别持有 Docker 管理权限，主应用和处理容器均不持有。主应用与管理服务全部失效时，监督仍独立运行；保证的前提是看门狗、Docker 引擎、宿主调度与时钟可用，不承诺宿主或 daemon 整体失效时的墙钟上限。生产阈值与负载余量需单独验收。

业务取消立即禁止成果提交；进程状态和清理状态独立记录，清理失败保持 UNKNOWN/RETRY_PENDING，恢复后重试确认，不将业务终态等同于进程已停止；未确认清理期间拒绝新增任务。已补证两个活遗留容器的启动回收、迟到成功响应经过实际成果提交入口的拒绝、删除拒绝与管理服务到 Docker 通信失败后的持久记录及重试。外部期限最终样本在容器创建后 15.235 秒确认删除，对照容器未被误删。见[第三阶段完整报告](../prototypes/sandbox-validation/ROUND3.md)。#8/#6 保持开放等待最终证据审阅，不等同于生产上线验收。

## 最终收口 · 2026-11-12

2026-11-12 用户已接受最终验证结果与限制，[#8 接入验证](https://github.com/BurnerK/iWork/issues/8#issuecomment-6826203433)与[#6 架构决策](https://github.com/BurnerK/iWork/issues/6#issuecomment-6826209370)均已完成收口。生产 Linux、正式身份、真实解析器、数据库成果事务及恢复等仍待实施验收；停止上限依赖看门狗、Docker、宿主调度与时钟可用，探针时间不是生产 SLA。
