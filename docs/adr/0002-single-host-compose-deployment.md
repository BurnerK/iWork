# 首版采用单机 Docker Compose 部署

当前状态：2026-11-12 用户已接受第三阶段验证结果和限制，#8 与 #6 均已收口。下文按阶段保留决策历史；最终方案见末尾独立执行看门狗补充与收口记录，早期“待验证/待审阅”不代表当前状态。

2026-11-12 确认：首版以单台 Linux 服务器与 Docker Compose 为标准部署方式，部署主应用与 MySQL，使用持久文件目录保存资料及成果。前端构建后随应用交付，暂不引入 Redis、消息队列或 Kubernetes。首版面向少量内部用户，选择较低的部署和维护成本，接受维护窗口内短暂停机，不提供多机高可用。

应用、数据库及持久文件统一纳入升级与备份流程，升级前备份，恢复时协调数据库记录与文件内容。实际服务器规格、模型服务及备份位置在部署准备时落实；备份恢复尚未验证。文件处理执行环境的具体隔离与管理方式仍待确定，不因采用 Compose 就视为已完成隔离设计。

该决定承接 [首版主应用与执行边界](0001-first-release-application-and-execution-boundaries.md)。[整体架构基线](../first-release-architecture.md) 已共同确认；沙箱接入仍待验证，[模块与部署议题 #6](https://github.com/BurnerK/iWork/issues/6) 尚未收口。

2026-11-12 验证补充（非新决议）：[#8 探针](../../prototypes/sandbox-validation/README.md) 已取得受控容器处理、隔离与生命周期正反向证据。普通 Docker socket 直连扩大主应用权限；SDK stop/超时/调用取消与主应用崩溃不保证处理进程停止。显式 shutdown 和启动回收可补充生命周期，但管理权限及是否增加受限管理服务仍待用户讨论。原决议保持，不能据此将 #6 或生产隔离标记为验收通过。

## 2026-11-12 沙箱接入修订（用户已确认）

单机 Compose 在主应用与 MySQL 之外增加受限沙箱管理服务。仅管理服务挂载容器管理接口；主应用通过内部控制网络提交固定处理任务，控制接口不发布宿主端口。管理服务独立持久化任务容器管理记录，不持有数据库或模型凭据，成果与业务状态仍由主应用保存。此组件不是完整的智能体运行服务拆分。

按任务配置隔离、资源限制和终止/回收策略，管理服务启动时核对遗留资源，确认实际删除后报告清理成功。主应用与管理服务分别失效的行为已由 [#8 探针](../../prototypes/sandbox-validation/README.md) 验证；生产 Linux、密钥管理、服务可用性与对不可信程序的容器外强制期限仍需验收。此次不增加 Redis、消息队列或 Kubernetes。

## 2026-11-12 独立监督部署补充

按用户“容器外期限、管理服务失效后也有上限”的要求，最小方案增加一个 Compose 执行看门狗，复用现有 Java 镜像，不新增队列、数据库或 HTTP 接口。它无网络、无业务凭据，仅持有 Docker socket 和自己的健康记录目录；管理服务只读该记录，过期后拒绝新任务。管理服务与看门狗均为高权限组件，此条取代前文“仅管理服务挂载容器管理接口”的描述。看门狗配置自动重启，恢复时按原创建时间检查任务；不从重启时刻重置期限。

独立监督、两个活容器启动回收、清理失败重试与迟到发布已获最小实测支持，见[第三阶段报告](../../prototypes/sandbox-validation/ROUND3.md)。Docker 引擎/宿主不可用时无法保证墙钟期限，应保持未确认状态并在恢复后回收；生产 Linux、部署容量与时限余量仍需验收。#8/#6 最终审阅状态不变。

## 2026-11-16 #11 登录态修订（用户已批准）

为正常重建后保留登录，增加官方 Redis 服务保存 Spring Session，取代此前“不增加 Redis”的限制。Redis 使用固定版本和镜像摘要、AOF 持久命名卷、健康检查与仅内部网络，不发布宿主端口，不保存用户/会话等业务数据。应用 readiness 同时检查 MySQL、Redis 和文件目录；Redis 不可用时认证相关请求失败关闭，返回 503，无内存降级。

MySQL 是账号、权限版本及个人会话的权威。Redis 丢失后重新登录即可；不兼容应用升级可使旧登录失效。AOF everysec 不是断电零丢失保证，生产升级/备份恢复仍另验。详见 [实施合同](../issue-11-design.md)。
